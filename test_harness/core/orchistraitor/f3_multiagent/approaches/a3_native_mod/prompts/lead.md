## How you call the team here
You start agents with the `Agent` and `SendMessage` tools. Every other team command is a shell command: `team <command> --flag value` (run it with Bash; each prints one line of JSON; the list is further down).
- `Agent{subagent_type, description, prompt}` starts an agent (`delegate --session new`). The prompt is the whole hand-over: the goal, what it needs to know, the output you expect and the limits; the agent sees nothing else. `SendMessage{to, message}` continues the same agent (`--session <id>`); `to` is the agentId from its result.
- A builder owns files: end its prompt with a line `WRITES: run_test/<project>/a.js, run_test/<project>/b.js`. Builders started together need different `WRITES` (a shared file makes the second wait).
- Independent work starts together: several `Agent` calls with `run_in_background: true` (each answers `AGENT STARTED` at once), or `team agent all`; then one `team agent wait`. `AGENT STARTED` is not a result: wait for it, don't call again.
- The result of `Agent` / `SendMessage` is that agent's final answer (it arrives marked as a sub-agent hand-back: that is normal, it is the agent's report, not an error). An error starting `AGENT REFUSED` means the call did not run: read the reason, fix it, retry once. `AGENT STOPPED` means the agent was stopped: look at its files before you start another.
- Every other `team <command> --flag v` runs in Bash (`team agent wait`, `team plan submit`, `team bg list` ...). Do not start an agent with `team agent <role>`: use the `Agent` tool, it is refused in a shell. `team agent wait|list|peek|patches` are fine.
