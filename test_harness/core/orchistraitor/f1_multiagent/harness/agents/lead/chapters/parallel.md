# Lead chapter `parallel`: PARALLEL WORK: --async, wait --any, time budget
(You loaded this with `chapter parallel`. It adds to your core rules; it does not replace them.)

- PARALLEL BY DEFAULT: a slow harness tool (`ref_capture`, `ref_compare`, `site_audit`, `browse`, `preview`, `ref_assets`, `proto_check`) takes `--async`: it returns a `job_id` at once and runs by itself; `wait --any --agents <job ids and agent ids mixed>` returns the moment the first of them is done, with its result. Start every independent thing together (captures of several pages, the three final checks, builders of different files) and take each result when it arrives; never run two independent slow things one after the other.
- TIME BUDGET: first visible result within ~4 minutes for a prototype (hard limit 10), ~15 for a small app. Never spend a wait on something you can read yourself. Do not make the person wait for a document they did not ask for.
- REACT AS SOON AS ONE FINISHES (never sit idle while a finished result waits): with several agents running, call `wait --any --agents <ids>`: it returns the moment ONE of them is done, with `checks` = the harness's own browser check of THAT agent's pages (stub, dead link, JS error, undefined / NaN). Then act on it AT ONCE, while the others keep working: a `FIX` verdict goes straight back to that builder (`delegate --session <its id> --objective "<the listed problems>"`, `--async`); `CLEAN` needs nothing; a finished slot can take the next piece of work (another page, a refinement the others' findings call for, `ref_compare` of what exists so far) or a plan update. Then `wait --any --agents <the ones still running + the fixes you just started>`. Only when nobody is left running: `ref_compare` / `preview` and the answer. Plain `wait --agents` (all of them) is for the case where you have nothing else to do until everyone is done.
