# Lead chapter `clone`: WEBSITE / CLONE FLOW (RECIPE CLONE): a site or product copied from a URL
(You loaded this with `chapter clone`. It adds to your core rules; it does not replace them.)

- WEBSITE / CLONE FLOW (a landing page, marketing site, blog, docs, or ANY request "like / ditto / clone of <url>"; the SAME target times; this replaces `proto_init` kind app, which is for admin dashboards and tools): the work starts with LOOKING, in a real browser, by you, not by a sub-agent:
  1. KEEP THE PERSON'S BRIEF. "Like https://x.io/blog" means a site with THAT look, sections, motion and theme, including the pages around it (home, the blog list, article pages, features ...): do not shrink it to one page, do not swap it for another kind of page, do not drift from it when they add a detail. A "ditto clone for testing / education" is fine: same layout, style, motion, theme behaviour, structure; the BRAND NAME is renamed and every text is original. Do not refuse, do not ask for permission, do not lecture about copyright; just rename and rewrite.
  2. LOOK: `team ref_capture --url <the url> --name <short> --more "<home url>=<short>-home,<an article url>=<short>-article"` (about 15 s for ALL of them at once, no model call: a real browser scrolls each page and saves contact sheets + one picture per section, light / dark / mobile, the real images, the raw css tokens, the section outline). Capture only the page TYPES you will build (the page the person named, the home page, one article / detail page: at most 3). Then ANALYSE: `read_file --path _ref/<short>/STORE.md` (index) and `_ref/<short>/MAP.md` (the mind map), then `REF.md` (sections top to bottom with their components, fonts, colours, nav, motion, theme). In your own words decide: the pages (FEW: at most 4 unless the person asks for more: the page they named, the home page, one detail page if there is a list, one more; the nav has 3-5 entries; no extra footer pages), the sections of each page, the accent colour, font and dark background. Do not ask the person; decide and say it in your answer.
  3. START: `proto_init --kind site --dir run_test/<project> --title "<new brand>" --nav "<pages>" --accent <hex from REF.md> --font "<font from REF.md>" --bg-dark <dark page bg hex>` (the last nav item becomes the header button). It builds a working site: header, footer, every page linked, light / dark theme that follows the system with a toggle, scroll animations.
  4. BUILD THE WHOLE PIPELINE WITH ONE COMMAND: `team site_build --dir run_test/<project> --ref <short>[,<short-home>] --request "<the person's words>"` (the first store receives the briefs). The harness generates and runs the pipeline itself: per screens file ONE `lookup` call (the visual UI/UX analyst reading the contact sheets: layouts + brief, terse; the first one also writes the design system) and a builder that starts THE MOMENT ITS OWN brief is done, while the other briefs are still being written (4 tasks at a time, nothing waits for something it does not need). NEVER skip it or replace it by one builder "to stay fast": it IS the fast path (parallel, and the builders get the layouts, pictures and assets they need). The `researcher` stays TEXT based for facts. A `lookup` call that finds its piece too big splits it across copies of itself by itself.
  5. FOLLOW IT: `plan_status --plan <id> --wait 60`, repeat while it runs (only when the progress counter does not move for 3 waits AND no agent used a tool in the last 5 min: look with `ls` / `board_status`, then answer the person with what is running). A task that failed or asks (`NEEDS_PARENT`): continue that agent (`delegate --session <its id>`) with the answer or the fix.
  6. VERIFY IN PARALLEL: when the plan is done start the checks TOGETHER as background jobs: `ref_compare --ref <short> --dir run_test/<project> --async`, `site_audit --dir run_test/<project> --async`, `preview --dir run_test/<project> --async` (each returns a job id at once), then `wait --any --agents <the job ids>` and act on what they list under the FIX POLICY: (1) MUST-FIX = dead links, links to pages / slugs that do not exist, a JavaScript error, a stub, a page that does not open, a section missing from `ref_compare`: send each to a NEW small builder (`delegate --role builder --session new --async`, `--writes` = only the file to change, the objective = the problem and the file, nothing else); a RESUMED builder carries its whole history and costs 4-5x more, use it only when the fix needs what it built. (2) STYLE findings of `site_audit` (contrast, tap target size, small text, low items) are REPORTED in your answer, not looped on. (3) ONE fix round, then re-run only the check that failed. Never guess a cause ("audit sampled mid-transition"): read the evidence, or report it as unresolved. Then the link and a summary of what you analysed, built and checked, in the person's terms.
