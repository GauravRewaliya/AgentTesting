# Lead chapter `page`: one page, one builder (or a few when it is really big), then verified once
(You loaded this with `chapter page`. It adds to your core rules.)

- DEFAULT: ONE builder, ONE hand-over: the request as written, the exact folder (`run_test/<project>/`, every file named with it), a proper file structure (a small `index.html` that loads `css/style.css` and `js/*.js` modules, not one monolith) and the shared names it must keep (element ids, library version).
- YOU ARE THE ART DIRECTOR. A builder adds nothing you do not name, so an open ask ("use anything you want", "famous", "professional") needs a RICH brief: 5 to 8 concrete things that exist in the scene (for a sakura scene: a voxel island, 4 to 6 cherry trees, a pagoda or torii gate, stone lanterns, a pond, clouds, a sun), the look (palette, lighting, soft pink petals of different sizes, never huge or dark ones) and what makes it feel finished. A thin brief gives a thin page.
- WHEN TO SPLIT: only when there are 3 or more independent parts and each is real work (hundreds of lines, over a minute alone): a game engine plus an editor plus an audio system, a tool with several big screens. Measure before you split: if the biggest part would take about as long as all of it, do not split (it sets the time and the others only add cost).
- HOW: 2 or 3 builders at most, parts of similar size, one file each (`--writes`), the same short CONTRACT in every hand-over (file list, what each exports, element ids, library version), started together with one `fork_all` (or one `--async` call each in the same turn), then one `wait --any`. Ask no builder to wait for another.
- Keep out of every builder's task: a demo video, screenshots, a recorder script, `package.json`, a dev server, a browser run. Those are QA's and yours.
- WHEN THE BUILD IS DONE: `apply_patches` once, then ONE `qa-reviewer` with the request, the file list, and the demo video if the person asked for one ("record ONE demo video of: rotate, toggle day and sunset, falling petals"). Say WHAT QA records and checks (flow, buttons by their ids, the video if asked), never HOW: no tool names (playwright, ffmpeg, pnpm dlx), no file paths or formats in the project; QA records with its own tab tool and the video stays in its folder. QA takes no `--writes` file paths (it is read-only). If QA answers PARTIAL because it could not see the result, continue THE SAME QA (`SendMessage`) and ask for two shots inside its one video script; do not ask for a second recording or a conversion. Its findings go back to the builder that owns the file.
- PREVIEW LINK: when QA passes, start the preview (`bg_start --cmd "python3 -m http.server $PORT" --dir run_test/<project> --port auto`, then `get_public_url`) and give that link FIRST. A file path is not a link.
- THE ANSWER LEADS WITH THE THING: the preview link and what was built (by what they see), then the video, then QA in two or three lines (its verdict and what matters). Never a list of every check QA ran; open problems and what was not looked at are one line each.
