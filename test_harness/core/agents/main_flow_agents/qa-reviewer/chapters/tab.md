# QA chapter `tab`: the browser tab, snapshots and the video
(You loaded this with `team chapter --name tab`. It adds to your core rules.)

- YOUR BROWSER TAB (like a person's browser, kept open): `team tab open --url <url>` ONCE, then `team tab do [--video] [--clear] --steps '[...]'` runs a WHOLE script on that same tab. There is ONE report and ONE video for your whole session: every script adds to them, you never name a folder (an `--out` is ignored); `--clear` only on your first script. Every reply ends with a SNAPSHOT of the page as it is now: each thing a person can press or fill with a ref like `@e5`; write the next script from it and target by ref (`{"click":"@e5"}`, `{"fill":{"@e3":"text"}}`), never guess selectors from the source code. Steps: `{"goto":url}`, `{"waitfor":"#id"}`, `{"click":"#id or button text"}`, `{"fill":{"#email":"a@b.c"}}`, `{"type":"#box","text":"hi"}`, `{"key":"Enter"}`, `{"viewport":"390x844"}` (phone; `820x1180` tablet; `1280x720` back: the layout is re-checked there), `{"scroll":900}`, `{"wait":2000}`, `{"eval":"js"}`. Give a step a `"name"` and it is numbered 0,1,2.. with its own picture (named for you, like `03_after-click.png`: never choose picture names) and its time in the video; the tool writes `index.html` (video on top, thumbnails jump the video to each step) and prints every FULL path: look at the pictures with Read by exactly those paths (evidence is stored in the session's store/qa, never in the project) and quote them in CHECKED; never search for files. The first failed step stops the script: the reply names it, says why and how many steps did not run, and shows the page as it is (snapshot + picture); correct it and send the REST. So write the WHOLE flow from the plan's Done-when list in ONE `tab do`, read the result, then a second script only for what failed. `--background` queues a script and returns at once (several can be queued; they run in order; read the outcome with `team tab result`): use it to keep working (read code, check the next thing) while the browser runs. A click waits up to 4 s for its target, so you need no `waitfor` for normal loading. The FIRST script of a QA task uses `--clear` (it removes the old pictures, video and report of that `--out` name, so the folder holds this run only); later scripts of the same task do not. ONE video per `--out` folder (`session.webm`) grows with every script: it records only while a script runs, so your thinking time between scripts is never in it (automatic pause and resume; never record twice for one task). Each step's number and name is drawn on the page itself (bottom left), so the video and the pictures show which step they are. Nothing reloads between scripts; do not wait or sleep in loops. `team tab close` when done.
- ONE script, ONE video: put the whole flow (and every toggle: day/night, theme, viewport) into ONE `tab do --video`. The video is final when `team tab close` returns (it waits for the encoder, which can take a minute on a busy machine, and names the file with its size): never record it twice, never copy or convert it (no ffmpeg, no sleep loops). When a video is the deliverable or already shows a state, take no separate picture of it. A VISUAL deliverable (a 3D scene, a page look) needs your eyes even when pictures are off, so take ONLY the pictures you must look at to judge: ONE of the main view, and ONE more only when a toggle changes how it looks (day to sunset, light to dark). Never a picture to prove motion (the video and an `eval` of the state prove it), never two pictures of the same state, never a picture of a state you do not need to judge. Put them as steps with `"shot":true` inside the one `--video` script, then look at each with `Read`. The tool keeps at most two pictures per session and says so when it drops one.
- Every `tab do` reply lists your pictures with their full paths and how many are left: look at them with `Read`, never hunt for a path or shoot again to find one. A toggle that fades or animates (day to sunset) needs time: `wait` 3000 before its picture. A picture taken too early is taken AGAIN with the SAME step name after a longer wait: it replaces the first and costs nothing. `team browse` is for a one-off look (a dark scheme, a file); for you it shares your session folder and the same two-picture limit, so use `tab do` for the page you are testing.

- A picture you will JUDGE (quality) must be repeatable: put `{"seed":1}` as the first step of that script (it replaces `Math.random` with a seeded generator, so petals, sparks and particles made afterwards are the same on every run), switch auto-rotate off with the page's own button, `wait` for fades, then take the picture. On a re-check take the same pictures again (same step names) and compare them with the earlier pass instead of judging from scratch.
