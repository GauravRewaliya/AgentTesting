# agent_fixture

Everything a **mocked sub-agent** needs, so the tests judge the *orchestrator* (does the lead call the right sub-agent with a good hand-over?) without paying for a real sub-agent run.
Not a suite: it has no `main.ts`, so the case loaders (`testrun/cases.ts`, `ui/.../server/data.ts`) skip it. Path constant: `FIXTURES` in `test_harness/core/paths.ts`.

```
agent_fixture/
  results/            recorded sub-agent answers, NESTED by suite = the same folder names as TestCases/test_folders (type ResultModule, ./types.ts)
    test_basic/  test_basic_2/  test_expo_go/  test_expo_proj_planning/  test_expo_sub_agent/  test_handover/  test_pipedream/  test_workflows/
                        (a result belongs to the suite whose cases expect it; validate.ts fails when it is filed elsewhere; suites with allow_real_subAg have none)
  store/              files those answers copy from + guard rules
    <name>_rules.json   role-order guard rules, picked by Case.guard   (type Rule, harness_own_custom/core/guard.ts)
    expo_go_rules.json  expo-go: hand-over must name run_test + PLAN.md, >= 120 chars
    expo_go/            the expo_go fixtures (below)
    expo_examples/ lock-issue/ lsp_trap/ pd_src/ legacy/   fixtures of the other suites
  index.json          GENERATED by `bun test_harness/core/build_index.ts` (type IndexRow): find a result without opening it
```

## How a call is served (harness_own_custom/main.ts)
1. The lead calls a sub-agent (`Agent` tool). The guard (`Case.guard` -> `store/<file>.json`) can stop it: thin hand-over, wrong role order, forbidden role.
2. `Harness.lookup(agent, task)`: a result whose `match.keywords` are ALL in the hand-over (case-insensitive) wins; otherwise the result without keywords whose `expected_input.text` is most similar (cosine >= 0.15). No hit = `NOTFOUND`, shown in the report as a miss.
3. `result.run(req)` does the work: `req.cp(from, to)` copies from `store/`, `req.write(path, text)` writes into the workspace (`run_test/`), and the returned string is the sub-agent's reply.
4. A *follow-up* to a session (`SendMessage`) is NOT served by a result: it is answered from that session's own history. That is why every expo_go phase is a new call.

## Data structures
| What | Where | Type |
|---|---|---|
| a recorded result | `results/<suite>/<file>.ts` default export | `ResultModule { id, title, description, match?{agent,keywords[]}, expected_input{text,guardrails_test}, run(req) }` |
| what `run` receives | `Req` | `{ agent, task, ws, store, cp(), write() }` |
| index row | `index.json` | `IndexRow { id, file, title, agent?, keywords?, text, copies? }` |
| guard rule | `store/*_rules.json` | `Rule { requires_done?[], contains_all?[], min_chars?, forbidden? }` per role |

## store/expo_go (all shapes declared in `test_expo_go/lib/types.ts`, validated by `lib/data.ts` at load and by `lib/check.ts`)
```
sources.json     SourceEntry per fixture: ref, url, repo, sha, path, kind (FIXTURE_KINDS), committed, fetch, expo_go verdict
phases.json      PhaseRow[] per project (GENERATED by make_patches.py): n, sha, from, folded, snapshot?, legacy_pins?, subject, patch, files
patches/<name>/NN_<sha>.patch   the diff of phase NN (lockfiles/images/fonts/READMEs left out); never given to the agent
bases/<name>/    start state of phase 1 (absent = empty start); package.json already at the repo's latest versions
examples/        committed final trees of the expo/examples we use (tailwindcss, storybook)
apply.ts         the shared work of every recorded expo-go result: copy base (phase 1), `git apply` the patch, write PLAN.md, return REPORT
fetch.sh         `fetch.sh <name> <dest> [n]` real checkout: state before phase n, or the pinned final state
make_patches.py  regenerates phases.json + patches/ from the git clones
```
Result files: `results/test_expo_go/role-expo-go-<case id>.ts` (most apply a real patch via `store/expo_go/apply.ts`; `eg_tw_02_spring`, `eg_tw_03_dark` and the rework pairs `eg_*_rework(_fix)` are hand-written). Case -> result link: `expected_agents_res: ["role-expo-go-<case id>"]`.
